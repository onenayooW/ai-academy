# Integrate API

ขั้นนี้ **เชื่อม frontend กับ backend API** แทน mock data จากขั้น 3–5 ยังไม่ปรับ UI layout ใหม่ เว้นแต่จำเป็นต่อการแสดง loading หรือ error — **ต้องรักษา responsive ที่ทำไว้ตั้งแต่ขั้น 2–5**

ก่อนเขียนโค้ด ให้อ่านแหล่งต่อไปนี้อย่างละเอียด แล้วสรุปสั้นๆ ว่าแต่ละหน้าจะเรียก endpoint ใดบ้าง:

- `AcceptanceCriteria.md` — Story 1–3 ทั้งหมด
- `DefinitionOfDone.md` — filter, sort, validation, error handling, แก้ไขภาพปก
- เอกสาร API ในโปรเจกต์ (เช่น `[path, e.g. /project/docs/API]`) — **ใช้เป็น source of truth สำหรับ endpoint, request และ response**
- หน้า frontend ที่ทำไว้แล้วจากขั้น 3–5

ถ้าไม่พบเอกสาร API, endpoint ไม่ครบสำหรับ AC/DoD, หรือ response ขัดกับ UI ที่มี ให้ถามก่อน ห้ามสมมติ endpoint หรือ field ที่ไม่มีในเอกสาร API

## ขอบเขตที่ต้องทำ

### 1. API layer

- สร้างชั้นเรียก API กลาง (เช่น service หรือ composable) ให้แต่ละหน้าใช้ซ้ำ
- ตั้งค่า base URL ให้เปลี่ยนได้ (เช่น `http://localhost:8080`, path `/v1/api/...`)
- จัดการ request/response ตามเอกสาร API (query params, JSON, `multipart/form-data` สำหรับอัปโหลดรูป)

### 2. หน้าแรก (Story 1)

| ฟีเจอร์ | การ integrate |
| --- | --- |
| แสดงรายการสินค้า | ดึงจาก API แทน mock data |
| Filter | ส่งเงื่อนไขกรองไป API (หลายเงื่อนไขพร้อมกัน) |
| Sort | รองรับ sort ตาม DoD: สินค้ามาใหม่, ราคา, ยอด click ดูมากที่สุด |
| ปุ่ม Line / โทร | ใช้ข้อมูลจาก API response |
| นำทางไปรายละเอียด / จัดการ | ยังทำงานเหมือนเดิม |

### 3. หน้ารายละเอียด (Story 2)

| ฟีเจอร์ | การ integrate |
| --- | --- |
| โหลดข้อมูลสินค้า | ดึงตาม id จาก route |
| แกลเลอรี | ใช้ URL รูปจาก API |
| ข้อมูลรถ / ผู้ขาย / ปุ่มติดต่อ | ใช้ข้อมูลจาก API response |

### 4. หน้าจัดการ (Story 3)

| ฟีเจอร์ | การ integrate |
| --- | --- |
| ตารางรายการ | ดึงจาก API |
| สร้าง / แก้ไข / ลบ | เรียก API ตามเอกสาร |
| อัปโหลดรูป | ส่ง `multipart/form-data` ตาม API spec |
| แก้ไขภาพปก | รองรับตาม DoD (เลือก/เปลี่ยน cover image ของ listing) |
| Validation | แสดง error จาก API (เช่น ชื่อซ้ำ `409`, ราคาไม่ถูกต้อง `400`) ร่วมกับ validation ฝั่ง client ที่มีอยู่ |

### 5. Error handling

- จัดการ loading state ขณะเรียก API
- แสดงข้อความ error ที่ผู้ใช้เข้าใจได้เมื่อ API ล้มเหลวหรือ validation ไม่ผ่าน
- จัดการกรณีไม่พบข้อมูล (เช่น สินค้าไม่มี — `404`)

## สิ่งที่ห้ามทำ

- ห้ามออกแบบ endpoint ใหม่เอง — ใช้เฉพาะที่มีในเอกสาร API
- ห้าม refactor UI layout ใหญ่ๆ ถ้าไม่จำเป็น
- ห้ามลบ mock data จนกว่าจะแทนที่ด้วย API ครบทุกหน้าแล้ว

## หลังทำเสร็จ

สรุปสั้นๆ ครอบคลุม:

1. ไฟล์ที่สร้างหรือแก้ไข
2. ตาราง mapping: หน้า/ฟีเจอร์ → endpoint
3. วิธีตั้งค่า base URL และรัน frontend + backend พร้อมกัน
4. error cases ที่รองรับแล้ว

หากมีสิ่งใดไม่ชัดเจนหรือมีคำถาม ให้ถามฉันก่อนดำเนินการเสมอ
