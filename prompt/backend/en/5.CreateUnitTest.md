Write unit / integration tests for the Truck2Hand backend to fully match docs and DoD.

## Sources of truth

1. Contract: `docs/API/*.md` (status, body, validation)
2. Validation: blocklist → `backend/src/config/blocklist.ts`
3. Existing code and conventions:
   - vitest: `npm test` / `npm run test:watch`
   - HTTP tests: `backend/src/test-app.ts` → `createTestApp()` (SQLite `:memory:`, temp uploads, seed catalog + admin + seller)
   - Examples: `products.test.ts`, `auth.test.ts`, `app.test.ts`, `blocklist.test.ts`

## Tech

- vitest 3.x, Node fetch with `app.listen(0)` on `127.0.0.1`
- `BCRYPT_ROUNDS=4` in test-app (faster)
- Image uploads in tests: `PNG_1X1` from test-app + FormData + Blob

## Required test types

A) Integration (HTTP) — use `createTestApp()` or the same pattern
   - `beforeAll`: createTestApp, login and store tokens by role
   - `afterAll`: `close()` to tear down server + sqlite + temp uploads
   - helpers: `authHeaders()`, `createProduct()`, `postJson()`

B) Pure unit — no server required
   - blocklist, seed builder, parse/validation helpers
   - test clear edge cases (substring vs whole word, etc.)

## Must cover (per DoD + docs)

Catalog:

- GET vehicle-types, brands, models?brand_id=

Products:

- POST create success, GET list paginate + filter AND + sort (newest, price_asc/desc, most_viewed)
- 409 duplicate title (including trim/case if implemented that way)
- 400 price, FK, model/brand mismatch, blocklist
- GET by id increments view_count; PUT does not increment view_count
- DELETE 404 / 200 + GET after delete returns 404

Product images:

- POST max 4, first image is cover
- PATCH cover, DELETE then cover / sort_order correct
- 400 when already 4 images / 404 when product missing

Health / docs (if `app.test.ts` exists):

- GET `/health`
- No deep Swagger UI testing required

Seed builder in code (if present, e.g. `seed-products.ts`):

- `buildSeedProducts`: count, unique title, FK, price/year range, 1–3 images per product, is_cover
- Not related to `docs/DataExample/*.csv` yet—that is the next step

## Writing rules

- describe/it names should read like a spec
- assert status first, then important body fields
- Do not rely on `docs/DataExample` or real `backend/data/app.db` — use `:memory:` + setup in tests
- Separate test files by domain (`*.test.ts` alongside src/)
- Do not mock the entire stack if integration is fast enough; mock only externals (e.g. seed image download) when needed
