# Design Database

Use only the following documents:

- `AcceptanceCriteria.md`
- `DefinitionOfDone.md`

Design the database schema without using information from any other documents or assuming features that are not explicitly specified.

## Tech stack

If specified in the DoD, use the following:

| Layer | Choice |
| --- | --- |
| Database | SQLite |
| ORM | drizzle-orm |
| Driver | better-sqlite3 |

Use SQLite data type names in the documentation (for example `INTEGER`, `TEXT`).

## Output requirements

- Save the files to: `[path, e.g. /project/docs/DB]`
- One table per `.md` file
- Each filename must be the table name in `snake_case` (for example `products.md`)

Use the following format for each file:

```markdown
# Table Name: {table_name}

Description: {Explain in Thai what the table stores and which page or feature uses it}

Source: [Link and a short supporting quote from the specification]

## Fields

| Field Name | Required | Data Type | Description | Example |
| --- | --- | --- | --- | --- |
| ... | Yes/No | INTEGER/TEXT/... | ... | ... |
```

If the table has constraints, indexes, or required seed values, add them after the Fields table. For example:

- **Constraint:** `UNIQUE(...)`
- **Required initial values:** (for master tables)

## Design rules

- Clearly separate master/lookup tables from transactional tables.
- For foreign keys, specify the relationship in the Description using this format: `FK → other_table.id`.
- If the specifications conflict or are unclear—for example, a filter references a field that is not present in the form—always ask me before proceeding. Do not make assumptions.

## After completing the design

Provide a brief summary covering:

1. List of tables
2. Foreign-key relationships
3. Insert order that avoids foreign-key constraint violations

If anything is unclear or you have any questions, always ask me before proceeding.
